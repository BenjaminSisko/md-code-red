## 4. Findings to fix

### M-1 (Major): NetworkManager backup and recovery commands break on space-bearing connection names

- **Where:**
  - `template.html:3289` copies form values into the runbook raw. Only the derived `remote_*` values are quoted (`shQuote` at `:3301-3304`); the binding function is `bindInstruction` (`:3279`).
  - The commands: `content/instructional.json:1036` and `:1040` (preflight) and `content/commands.json:666` (Recover).
- **What the shipped artifact renders** for `con = Wired connection 1`:
  - `nmcli connection show Wired connection 1`
  - `profile_file=$(nmcli -g GENERAL.FILENAME connection show Wired connection 1) && …`
  - The same unquoted lookup appears in Recover.
- **Why it fails:** the shell splits the name into three nmcli IDs, so the lookup fails and the `&&` chain stops. No backup is made and no restore happens. This affects "Wired connection 1", "System eth0" and "cloud-init eth0", which are NetworkManager's default names and exactly the case the fifth review asked to support. The modify command itself is correctly quoted (TC-MATRIX-025…028).
- **Why the tests missed it:**
  - `tests/test_remote_transfer_transactions.py:57` quotes `con` itself, which the app does not, and never executes nmcli.
  - `tests/test_instructional_ux.py:150-157` only checks that substrings are present.
  - No browser assertion reads the nmcli runbook.
- **Unverified, needs one host check:**
  - The repo's RHEL 8/9/10 nmcli captures don't document a `GENERAL.FILENAME` field. The corpus only uses the list form `nmcli -f TYPE,FILENAME,NAME connection`. If the per-connection view lacks that field, this step fails for every connection name. `test_instructional_ux.py:154` pins the field name as a string without evidence.
  - The backup file sits inside a directory NetworkManager scans, with a suffix NetworkManager may not ignore, so it could load as a duplicate profile.
- **Impact:** for a lockout-prone change, the pre-change backup and the documented recovery don't work, while CHANGELOG:13-14 claims both problems are closed.
- **Required fix:**
  - Shell-quote runbook values used in command context, or at least `<con>`. Preferably resolve the profile by UUID.
  - Confirm the filename field on RHEL 8, 9 and 10.
  - Store the backup outside NetworkManager-scanned directories.
  - Add an execution test that goes through the app's own binding with "Wired connection 1", plus a browser assertion on the nmcli runbook.

### M-2 (Major): SCP/rsync rollback silently fails for symlinked destinations

- **Where:** the preflights save the target with `cp -a` (`instructional.json:1826` for scp, `:1868` for rsync). Recover then moves paths, not contents (`commands.json:5784`, `:5846`).
- **What I ran:** the exact strings the browser rendered, through the fake-SSH harness with GNU coreutils.
  - **SCP to `link.conf → real.conf`:** preflight exits 0 but saves the link, not the file. After a write through the link, Recover exits 0 and `real.conf` still contains the transferred bytes.
  - **rsync to `linkdir → realdir`:** preflight exits 0. `du` measures the link (about 0), so the capacity check is also wrong. Recover exits 0, and the modified and new files remain.
  - I confirmed locally that rsync writes into a symlinked destination directory and keeps the link. That was macOS's openrsync; RHEL's rsync is not tested here.
- **Impact:** Recover reports success but restores nothing. This is realistic for `current → releases/…` deployment roots and RHEL's symlinked config paths, such as `/etc/sysconfig/selinux`.
- **Required fix:** either refuse symlinked targets in the preflight, or resolve the real path once (`readlink -f`), record it in the transaction, and back up and restore that path. Add symlink cases to the transaction tests.

### m-2 (Minor): Reference-tier acknowledgement leaves a stale success message

### m-3 (Minor): `.` path segments bypass remote-path normalization

- **Remote root:** `isRemotePath` compares the raw path to the literal `"/"` (`template.html:824`). So `root@h:/.` is accepted and rated red, not refused, for both scp and rsync.
- **Broken rsync preflight:** for rsync to `…/tree/.`, the transaction directory lands inside the target. The preflight then fails closed with "cp: cannot copy a directory … into itself".
- **Inconsistent rating:** `host:/srv/app/.` is yellow while `host:/srv/app/` is red.
- **Required fix:** normalize the remote path before validating, binding and classifying, or refuse `.` segments.

### m-4 (Minor): On mobile, a command-linked STIG opens off-screen

- **Evidence:** at 390×844, `RHEL-08-040101` opens its command with the Inspector on, but the STIG panel sits at y≈1589, about 750 px below the fold. The page does not scroll or move focus to it.
- **Other widths:** at 768, 1024 and 1440 px it is on screen. TC-STIG-SELECT-001 (`:370`) and TC-PIPE-CONTROL-002 run only at 1440 px.
- **Required fix:** scroll or move focus to the panel at narrow widths, and add a 390 px assertion.

## 6. Low-risk residuals (not blocking on their own)

- **Unsigned candidate:** the provenance placeholder is still in place. Host receipts cover RHEL 7/8/9/10 as 0/9/0/9, and RHEL 7 flags come from a UBI7 container.
- **No live execution:** transaction scripts were only run through fake SSH on local filesystems; nothing ran on a real RHEL host.
- **Verify step mixes prose and command:** pasting the "Copy Verify" payload prints `Confirm: command not found`, exits 0 and does not finalize. It fails safe, because the next preflight refuses the stale transaction. Making finalize its own copyable step would fix it.
- **"Copy complete plan" (since alpha.5):** if pasted into a shell, it would run Recover immediately after Run.
- **rsync `--dry-run` is rated Destructive:** conservative, but likely to cause warning fatigue.
- **Snapshot restore limits:**
  - Restoring a snapshot discards any changes made after the preflight.
  - Mount-point destinations fail closed.
  - Transactions carry no per-operation ID, so the preflight refusal is the only guard against reusing stale state.
- **Coverage:** screen readers are unverified, and only Chrome was tested.
- **Flag-coverage baseline:** its 2026-09-25 date has passed, but it was formally retired on 2026-09-20 and the expiry test passes. No issue.
